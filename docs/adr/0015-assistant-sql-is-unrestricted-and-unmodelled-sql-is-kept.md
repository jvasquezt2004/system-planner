# Accept any PostgreSQL from the Assistant and keep what the Design cannot model

Supersedes the "rejected, never approximated" consequence of ADR-0003. Schema
Designer is a sandbox, so the Assistant's SQL is not restricted to the subset the
Design can model. `apply_ddl` still translates what the Design represents
(tables, columns, indexes, enum types, functions, triggers, policies, comments)
into the same structured changes a hand edit produces, so the canvas, stable
identities and Undo keep working. Every other statement is kept verbatim as a
**raw SQL statement** in the Design and emitted with the generated schema, in
order, so the Design stays the single source of truth and the sandbox stays
rebuildable (ADR-0001).

Before anything is committed, a Design that gained raw SQL is run against a
throwaway PostgreSQL; if PostgreSQL rejects it nothing changes and its error goes
back to the Assistant. `DROP` of an object that raw SQL created removes that
statement (and the ones that only alter it). Data statements (`INSERT`, `UPDATE`,
`DELETE`, `SELECT`, `COPY`, `CALL`) are refused because the sandbox is rebuilt from
the Design alone; Scenarios run data.

Codex and OpenCode have file tools, so they get one schema interface instead of
statements: each Design's `schema.sql` in the Project folder is editable, and an
`apply_schema` tool reads it back. The text is translated into a Design, and every
object that still exists by name keeps its id, canvas position and notes. Provider
connections have no files and keep `apply_ddl`.

## Consequences

- A table that uses unmodelled features (such as `CHECK` or `GENERATED BY DEFAULT`)
  is kept as raw SQL, so it has no card on the canvas and is not in generated ORM
  code, but it is in the SQL preview, the sandbox, exports, and Turn revert.
- Raw statements that alter objects the Design also models run after them, so the
  SQL is right even where the canvas does not show the effect.
- `public.` is the default schema and is treated as unqualified.
- Only what PostgreSQL itself rejects stops SQL from being generated. Modelling
  preferences are warnings drawn from Supabase's Postgres best practices: a table
  with no primary key or no columns, an empty Design, a composite primary key, a
  single-column unique constraint, integer or text keys of different widths, `SET
  NULL` on a required column, and a primary key marked nullable are all valid
  PostgreSQL. Unindexed foreign keys, mixed-case names and `timestamp` without a
  time zone are advice too. Warnings appear in the SQL panel, in `schema.sql`'s
  header, and in what the Assistant's tools return.
